# План доработки Сеула для faf23442

Дата передачи: 2026-11-04. Заказчик и владелец: **KIR223**. Исполнитель: **faf23442, Claude Code**. Исходная ветка: `a/seoul-city-polish-20261104`; команды первого запуска — [START_FAF23442.md](../../START_FAF23442.md).

## Задача владельца

Сделать карту узнаваемым, плотным, живым Сеулом с реалистичными материалами, чёткой картинкой и устойчивой производительностью на RTX 2050. Исправить движение людей и машин, ориентацию машин на уклонах, недостаток и исчезновение трафика, отсутствующие здания/магистрали/высотки. **В этой передаче исправления выполняет faf23442; документ не означает, что дефекты уже устранены.**

Пользователь наблюдает 40–50 FPS (примерно 20–25 мс). Предыдущий локальный замер другого кадра дал 38,43 мс днём и 27,91 мс ночью при 1280×720. Это разные сцены/условия: сначала воспроизвести замер, а не объявлять один из результатов ошибочным. Цель проекта — 16,6 мс, 14–16 ГБ ОЗУ; точное разрешение, настройки и характеристики ноутбука записывать в каждом сравнении.

**Один этап за раз.** Для каждого: прочитать входные данные → воспроизвести → изменить → проверить → обновить прогресс и отчёт → коммит по-русски → push → отдельный PR. ## Этап 03. Единая дорога, тротуар, мост и высота поверхности

1. Сверить OSM и запечённые дороги с фактической видимой геометрией каждого района. Один набор данных должен определять дорогу для отрисовки, навигации, трафика и коллизии; исключить ситуацию «машина следует старому OSM под новой улицей».
2. Сохранить дорожные атрибуты: класс, полосы по направлениям, односторонность, разделители, переходы, тротуары, перекрёстки, bridge/layer/tunnel. Разноуровневые пересечения не соединять только из-за совпадения XZ.
3. Для моста/уклона сформировать согласованный профиль высоты дорожной поверхности и плавные съезды. DEM под рекой не является высотой мостового полотна. Вода, дороги и набережные должны согласовываться, без подъёма всего города одной константой.
4. Построить/обновить коллизии и навигационные поверхности. Повторить маршруты между районами; проверить проезд/проход в обе стороны физически, включая вход/выход из моста.

**Приёмка:** конкретные старый/новый район, склон, мост и разноуровневый узел совпадают по визуалу/физике/графу; нет проезда сквозь берег или под мостом. Уровень воды не принят только по красивому снимку. Тесты проекции, высот и разделения уровней плюс игровой проезд.

## Этап 04. Машины по полосам, люди по пешеходной сети

1. Автомобили: правосторонние полосы, направление, ширина/offset, поворот по допустимым соединениям, плавный путь через перекрёсток, безопасная дистанция и остановка за впереди идущим. Исключить срезание углов через тротуар, дома, встречную полосу и зелёные зоны.
2. Проверить знаки смещения и привязку машины к полосе, особенно поворотах и обратных направлениях; не чинить одну улицу глобальным случайным offset.
3. Пешеходы идут по тротуарам/дорожкам/пешеходным зонам; проезжую часть пересекают по разрешённым переходам. «Строго по дороге» для людей означает корректную пешеходную поверхность, а не движение посреди автомобильных полос. Не спавнить в зданиях, воде, ограждениях или на магистралях.
4. Проверить исходные точки, доступность назначения, обход препятствий, локальное избегание, зависших агентов и переходы между ячейками. Нет пути — корректная перепрокладка/ожидание, не телепорт на глазах игрока.

**Приёмка:** детерминированные тесты полос/поворотов/односторонности и запрещённых поверхностей; 30 минут смешанного городского прогона с журналом нарушений и числом агентов. Нет выезда/выхода за допустимую поверхность в контрольных сценах. Не заявлять полную симуляцию правил движения без реализованных светофоров/приоритетов.

## Этап 05. Реальное положение машины на подъёме и повороте

Подтверждённая точка входа: в `city_demo.cpp` автомобиль получает `terrain.heightAt(car.pos.x, car.pos.z)` в одной точке и `streetModelTransform(..., car.heading)`. Это не учитывает опоры/наклон корпуса и не отличает DEM от полотна моста.

1. Использовать поверхность дороги/коллизии из этапа 03. Для ближнего транспорта — контакт колёс/подвески через существующую физику Jolt или согласованные запросы к дороге; не писать отдельный физический движок.
2. Ориентировать корпус по продольному и поперечному уклону, интерполировать переходы «ровно → склон → вершина». Не менять один Y при горизонтальном кузове, не привязывать мост к речному DEM. Следить за клиренсом/отсутствием зависания колёс.
3. Для моделей подготовить отдельные колёса/пивоты и единицы; вращение от пройденного пути/радиуса, поворот передних колёс от траектории. Не обещать анимацию колёс на слитом меше без переработки модели.
4. Разделить ближний физический и дальний облегчённый транспорт; переключать без скачка позы. Лёгкое движение подвески должно следовать ускорению/дороге, без произвольного «качания для реализма».

**Приёмка:** видео сбоку на подъёме/спуске/поперечном уклоне/вершине/мосте; тесты нормали, ориентации, вращения и непрерывности; измеренный бюджет нескольких машин и плотного потока.

## Этап 06. Достаточная жизнь старых районов и устойчивый стриминг

Подтверждённая точка входа: в `city_demo.cpp` радиусы спавна/удаления трафика заданы 350/550 м. Это повод проверить причину исчезновения, не готовый диагноз всех провалов плотности.

1. Вынести плотность, активные лимиты и радиусы в профиль данных. Настраивать по классу дороги, району, часу и достижимому бюджету; не увеличивать общий лимит вслепую.
2. Разделить радиусы визуализации, полной симуляции, фоновой симуляции и удаления; добавить гистерезис. Машина не удаляется из-за краткой невидимости/поворота камеры и не появляется в кадре из воздуха. Сохранять ID/маршрут/состояние при смене LOD/ячейки.
3. Спавнить вне наблюдаемой области на корректной доступной полосе, учитывать занятые места. При удалении после реального удаления игрока — экономная фоновая запись/пересоздание, без требования бесконечно держать каждую машину в памяти.
4. Проверить поток во всех четырёх старых районах и Кандаме, переходах и развороте игрока; пешеходы тоже не должны зависеть от одного начального спавна у камеры. Учитывать загруженность районов и расписания взрослых архетипов.

**Приёмка:** заданный маршрут туда-обратно и 30 минут игры; стабильная плотность по утверждённому профилю, нет массовых исчезновений рядом/на глазах и утечки памяти. Таблица видимых/активных/фоновых агентов и кадрового бюджета. Число машин — результат измерений и приёмки, не произвольные «1000 для красоты».

## Этап 07. Реалистичные материалы всех используемых городских поверхностей

1. Инвентаризировать все видимые материалы: процедурный цвет/заглушка, корректный PBR, отсутствующая карта/неверный путь, нейтральный после конверсии. Пройти **все готовые районы**, не только 12 общих материалов или одну улицу.
2. Связать каждый тип поверхности с предоставленной библиотекой: разные корейские кирпичи, штукатурка/бетон, камень/цоколь, асфальт, тротуарная плитка, окрашенный металл, кровля, дерево, стекло. Сначала проверить 53 подготовленных набора и соответствие референсу, затем скачать недостающее с чистой лицензией.
3. Для каждого PBR проверить albedo без нарисованного освещения, normal (ориентацию осей), roughness, metallic, AO/ORM, sRGB/linear и масштаб рисунка в метрах. Настроить UV/тайлинг/стыки, высоту кирпича и плотность текселей. «Есть фотография в baseColor» ещё не реалистичный материал.
4. Вариации/грязь/потёки/декали применять осмысленно, не случайным шумом на каждом фасаде. Не удалять эмиссию вывесок/окон при замене стены. Проверить сухой/мокрый день и ночь.
5. Размеры выбирать по видимому размеру и VRAM: ближние важные поверхности подробнее, дальние — мипы/меньшее разрешение/общие наборы. Все текстуры с мипами и поддерживаемым сжатием. Не ставить 4K/8K на каждый объект.
6. Отдельно оформить Building Set; проверить нормализованный City 2 и остальные источники перед размещением. Исправить непереносимые локальные пути без коммита исходных архивов.

**Приёмка:** реестр покрывает 100% материалов реально используемых поверхностей выбранных районов; у каждой записи есть принятый PBR или обоснованное исключение (разметка/эмиссия и т. п.), нет незамеченных fallback из-за отсутствующих файлов. Кадры близко/средне/далеко, день/ночь/дождь; credits/manifest/VRAM/время проверены. Процедурное размещение геометрии не запрещено; проблема — примитивные материалы и неверные пропорции.

## Этап 08. Пустоты, магистрали, высотность и узнаваемая география

1. Для каждой пустоты из этапа 01 довести диагностику до источника: полнота bbox/тайлов/relations/multipolygon/building:part, фильтры дорог, пропущенные контуры, уровни/высоты, bake/stream/LOD/culling. Сравнить числа входных/приготовленных/видимых объектов.
2. Восстановить **реальные** отсутствующие улицы, магистрали, развязки, кварталы и силуэты. Учитывать число полос, реальные ширины, расстояния, мосты/съезды и топологию. Не заполнять парки, острова, стадионы, водные и охранные зоны домами.
3. Высотки располагать по реальным зонам/ориентирам и этажности; при отсутствии height использовать документированный районный профиль с ограничениями, а не равномерные случайные башни. Источник каждого важного ориентира/решения записать.
4. Использовать выделенные здания City 2/3/Building Set и модульные наборы после проверки масштаба, окон/этажей, коллизий и брендов. Не копировать один внешний город как якобы точный Сеул.
5. Приоритет районов: старый Мапо → переходы и связующие дороги → Кандам/Каннам и его силуэт → остальные районы по дизайну 06/72. Сначала один контрольный квартал, затем отдельные подэтапы 08a/08b/… с собственными PR; не «сразу весь Сеул» одним коммитом.
6. Источники географии — разрешённые открытые данные; фото/панорамы допускаются как референс согласно правилам, не извлекать закрытые 3D-тайлы/текстуры. Реальные логотипы заменять вымышленными.

**Приёмка:** сравнительные схемы и панорамы ключевых направлений, отчёт исправленных дыр/дорог/высоток, сохранённые парки и вода, связность и физический проезд после новой запечки. Узнаваемость проверяется на выбранных реальных местах; число зданий само по себе не критерий реализма. После каждого подэтапа перестроить зависимые графы/коллизии и повторить маршруты этапов 03–06.

## Этап 09. Доводка районов на уровне улицы

1. Пройти каждый заявленный готовым район: фасады первых этажей, витрины, входы/лестницы, корейские вывески вымышленных брендов, кондиционеры, провода там, где уместно, остановки, ограждения, урны/скамейки, растительность и уличный свет.
2. Сохранить особенности районов: масштаб переулков/рынков/скверов Мапо отличается от широких деловых улиц Каннама. Не превращать весь город в одинаковый набор вывесок и небоскрёбов.
3. Проверить существующие интерьеры и все 17 добавленных предметов: масштаб, опора на поверхности, двери, проходы, мебель/растения/продукты, коллизии. Новые помещения — по реальным пятнам застройки и бюджету.
4. День/ночь/дождь: читаемость, отсутствие пересвета, мерцания, z-fighting и «света сквозь стены». Вода/набережные должны соответствовать физическому профилю, отражения/волны — отдельное улучшение после корректной географии.

**Приёмка:** поквартальная ведомость и маршрутный осмотр с доказательствами, а не общая галочка «всё красиво». Проверять стриминг, навигацию и плотность после декора. Святыни/храмы — без насилия, весь городской контент — взрослый.

## Этап 10. Итоговая производительность и проверка целого города

1. Повторить исходные сцены на идентичных настройках, включая самые тяжёлые сочетания трафика/толпы/теней/ночного света и длительный переход между районами. Отдельно native 1280×720 для сравнения с прежними замерами и фактическое разрешение владельца; масштаб рендера указывать явно.
2. Оптимизировать доказанные затраты: LOD/HLOD, пространственное/дальнее отсечение, группы материалов и инстансинг, каскадные тени, alpha foliage, свет, загрузку текстур/ячеек и частоту обновления дальнего AI. Не повторять без проверки ухудшившую кадр группировку теней.
3. Не добиваться FPS скрытым снижением разрешения, удалением людей/машин/высоток или заменой принятых PBR на плоский цвет. Качественные пресеты допустимы, с явным описанием отличий и проверкой чёткости.
4. Цель — около 60 FPS/16,6 мс на согласованном профиле RTX 2050, без постоянных стриминговых рывков. Среднее, p95/p99, VRAM/RAM, пики и длительность измерения указать. Если бюджет не достигнут — этап остаётся открытым с измеренными узкими местами, без ложной галочки.
5. Чистая сборка/получение доступных данных, все тесты/графические сцены, Vulkan, повторный 30-минутный городской прогон и возврат в старые районы. Отдельный список того, что ещё не воспроизводится без локальных источников.

**Приёмка:** итоговый отчёт по всем исходным жалобам, каждая закрыта доказательствами; воспроизводимый запуск; фактические бюджеты; ссылки на PR всех этапов. Только затем просить владельца об общей художественной/игровой приёмке по DoD, не объявлять весь проект/восемь боевых стилей завершёнными.

## Команды проверок и отправки каждого этапа

В корне, preset адаптировать к Visual Studio. Не запускать тяжёлую подготовку ассетов параллельно с замером кадров.

```powershell
$env:PYTHONUTF8='1'
python tools/doctor.py
cmake --preset windows-release
cmake --build --preset windows-release --parallel
ctest --preset windows-release --no-tests=error
python -m unittest discover -s han/tools/pipeline/tests
python data/_tools/validate_data.py
python han/tools/pipeline/han_fetch.py verify
python tests/engine/screenshots/run.py --exe build/windows-release/bin/Release/han_scene_demo.exe
git diff --check
```

Python-тесты подготовки воды/старых форматов могут требовать numpy, mapbox-earcut, ufbx/Assimp и Blender. Окружение владельца `build/asset-tools` локальное, через clone не приходит. На машине друга поставить нужные зависимости в изолированное окружение и указать версии; не считать пропущенный интеграционный тест реально выполненным. GLSL менялся — запустить `python shaders/compile_shaders.py`, проверить изменения generated-файлов.

Запуск сцены (после получения согласованных данных):

```powershell
.\build\windows-release\bin\Release\han_city_demo.exe --walk --hour 13
.\build\windows-release\bin\Release\han_city_demo.exe --walk --hour 21
```

Для коммита перечислять только свои файлы, не добавлять всю рабочую папку с чужими инструментами. Затем:

```powershell
git commit -m 'Город: этап 01 — исходные измерения и воспроизведение дефектов'
$cityBranch = git branch --show-current
python tools/han_zones.py check --base origin/main --head HEAD --branch $cityBranch
python tools/ci/credits_check.py --base origin/main --head HEAD
# Только если проверки успешны:
git push -u origin $cityBranch
# Текст PR заранее записать в файл отчёта/отдельный временный файл.
gh pr create --draft --base main --head $cityBranch --title 'Город: этап 01 — исходные измерения' --body-file docs/codex/city_handoff/01_baseline.md
```

Это пример для этапа 01, имена менять по этапу; для зависимого PR вместо main использовать ветку предыдущего этапа. Проверка зон относительно main всё равно обязательна. Если любая проверка не прошла — исправить либо объяснить фактический блокер, не обходить её и не отправлять как готовый этап. Владелец получает ссылку на каждый этап, что сделано, что проверено и **«Следующие по плану»** с конкретной следующей работой.
