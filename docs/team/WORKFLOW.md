# Рабочий процесс команды

## День
1. Утро: `git pull --rebase origin main` в своей ветке; запусти Claude, напиши «Начинай» — он прочитает прогресс и Issues и продолжит.
2. В течение дня: маленькие коммиты в свою ветку; Claude обновляет `docs/progress/<роль>.md` в конце сессии.
3. Вечер: PR хотя бы раз в 1–2 дня (даже маленький), пока сборка и тесты зелёные. В чат команды — 3 строки: сделал / делаю / жду от других.

## Неделя
- В выбранный день все вливают свои PR в `main`; A собирает «недельную сборку» (Release) и выкладывает её (GitHub Release или общий диск).
- Владелец играет, пишет замечания Issues с меткой `playtest` и зоной (`zone-a/b`). Замечание без зоны — владелец ставит зону сам.
- Проверка вех: `docs/design/64_…` (Definition of Done) и список «Готово, когда» этапов в `docs/team/STAGES_*.md`.

## Быстрый путь: одна команда
`python tools/ship.py -m "Что сделано по-русски"` — коммит, проверка зон, push в свою ветку, Pull Request. Дальше всё делает GitHub (см. `AUTOMATION.md`).
Ручные команды ниже нужны только если автоматика сломалась.

## Ветки и PR
- Ветки: `a/<этап>-<суть>`, `b/…`, `o/…` (владелец). Если один человек — и A, и владелец: правки общих файлов (`docs/design`, `docs/team`, `tools`, `CLAUDE.md`) только в ветках `o/…`, работа движка — в `a/…`; проверка зон смотрит на префикс ветки. Пример: `b/g1-combat-core`.
- `main` всегда собирается. Сломал `main` → чинишь первым делом или откатываешь свой PR.
- PR по шаблону. Метка `contract` — если трогаешь `contracts/`. Одобряют владельцы затронутых папок (CODEOWNERS) и все потребители контракта.
- Перед PR: `python tools/han_zones.py check --base origin/main --head HEAD` — проверка зон (то же сделает CI).
- Конфликт слияния в чужом файле → не решай сам, напиши владельцу файла.

## Две сессии Claude у одного человека
Только через `git worktree`: `git worktree add ../han-b2 -b b/g2-boxing-minigames origin/main` — отдельная папка и ветка. Личные файлы
(`CLAUDE.local.md`, `.claude/settings.local.json`) скопируй туда же или запусти `python tools/make_personal.py --role B` внутри новой папки.

## Что делать, если нужна правка в чужой зоне
1. Issue по шаблону «Задача для другой зоны»: кому, что, зачем, как будет вызываться.
2. Если это интерфейс — PR в `contracts/` (метка `contract`) + заглушка.
3. Работай дальше на заглушке. В `docs/progress/<роль>.md` в «Блокерах» пиши номер Issue.

## Общие файлы, где раньше были конфликты (и как их разнесли)
| Было | Стало |
|---|---|
| один `PROGRESS.md` | `docs/progress/A.md B.md` |
| один `CREDITS.md` | `docs/credits/A.md B.md`, склейка на E15 |
| один `ru.csv` | `data/loc/<язык>/<зона>.csv`, чужие строки — `contracts/loc_requests/` |
| корневые CMake и `vcpkg.json` | только A; модули подхватываются автоматически |
| один `ARCHITECTURE.md` | `docs/arch/A.md B.md` |

## Аварийные кнопки (только владелец)
`HAN_ALLOW_MAIN=1 git push origin main` — разрешить push в `main`; `HAN_ALLOW_ZONE=1 git push` — отключить проверку зон. Использовать только для починки.
