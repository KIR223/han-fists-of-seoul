# HAN: Fists of Seoul — правила Claude для команды (общие для всех)

Игра: 3D, вид от третьего лица, открытый мир Сеула, главная фишка — рукопашный бой (8 стилей), строго 18+.
Свой движок HAN Engine (C++20 / Vulkan 1.3 / Jolt / Lua). Цель: RTX 2050, 14–16 ГБ ОЗУ.
Только бесплатные ассеты с чистой лицензией и вымышленные бренды. Работаем вдвоём: A (он же владелец) — движок, мир и город; B — бой, сюжет и игра.
Отвечай по-русски, коротко. Полный дизайн — `docs/design/` (оглавление `docs/design/INDEX.md`).

## 1. Старт каждой сессии (по порядку; если роль известна — ничего не спрашивай, просто делай)
1. Твоя роль — в `CLAUDE.local.md` (строка `РОЛЬ: A|B|OWNER|A+OWNER`; `A+OWNER` — разработчик A, он же владелец проекта: твои правки владельца идут в ветках `o/…`, работа A — в `a/…`). Файл роли и прогресс подключены оттуда автоматически.
   Если роли нет — сначала выполни `python tools/join.py` (роль определяется по логину GitHub из `tools/team.json`, сам создаст личные файлы и перейдёт на ветку `<буква>/start`). Если не вышло — задай ОДИН вопрос: «Какая у тебя роль? A — движок, мир и город (владелец); B — бой, сюжет и игра»,
   потом выполни `python tools/make_personal.py --role X` и продолжай.
2. Если `git config core.hooksPath` не равен `.githooks` — выполни `python tools/setup_local.py` и покажи итог.
3. **Только владелец (роль `A+OWNER`), если `git remote get-url origin` ничего не вернул** — репозитория на GitHub ещё нет. Сделай всё сам:
   проверь `gh auth status` (если не вошёл — попроси пользователя выполнить `gh auth login`), спроси логин GitHub разработчика B (если пользователь его ещё не дал)
   и запусти `python tools/bootstrap_github.py --b <логин B>`. Скрипт создаст приватный репозиторий, отправит `main`, создаст ветки `a/start` и `b/start`,
   пригласит B, создаст метки и положит в корень файл `JOIN_HAN.ps1`. Покажи итог и скажи: «Отправь B файл JOIN_HAN.ps1 — больше ему ничего не нужно».
   Если у B ещё нет GitHub — запусти без `--b`; позже, когда пользователь пришлёт логин, выполни `python tools/add_member.py --role B --login <логин>`.
   Затем: убедись, что ты НЕ в ветке `main`. Ветки: `a/…`, `b/…` и `o/…` (владелец); **ты можешь отправлять на GitHub только ветки своей буквы**
   (хук и запреты это проверяют). Первая сессия — ветка `<буква>/start` уже есть на GitHub: `git fetch && git checkout <буква>/start`, дальше новые ветки от `main`.
   Затем `git pull --rebase origin main` (если есть remote и нет несохранённых правок).
4. Прочитай свой прогресс (`docs/progress/<роль>.md`) и открытые Issues зоны: `gh issue list --label zone-<роль>` (если `gh` есть).
5. Прогресс пуст (ни одной галочки) → это первая сессия: покажи план из ≤10 строк и выполни свой раздел `docs/team/FIRST_TASKS.md`.
   Иначе → продолжи с первого незавершённого этапа из прогресса.
6. Читай только части дизайна, нужные этапу (`docs/team/READING_<роль>.md`). Часть 00 — для владельца, пропусти.

## 1а. Автоматика (подробно — `docs/team/AUTOMATION.md`)
- **Сообщения коммитов и заголовки Pull Request — только по-русски** (пример: «Бой: кадровая машина ударов (G1)»). Хук `commit-msg`, хук Claude и CI это проверяют.
- Отправка работы — одной командой: `python tools/ship.py -m "Что сделано по-русски"` (коммит → проверка зон → push в свою ветку → Pull Request).
  Слияние в `main` происходит само, когда проверки зелёные; PR с метками `contract` и `needs-owner` одобряет владелец. Вручную `git push` не нужен.
- Хуки Claude (`.claude/settings.json`) сами подтягивают ветку при старте, не дают править чужие зоны даже через shell и в конце сессии напоминают обновить прогресс.
- Среда не работает → `python tools/doctor.py --fix`. Сборка и тесты → `powershell -File tools/build.ps1`.
- Новый ассет (картинка, звук, модель, шрифт) без записи в `docs/credits/<буква>.md` с свободной лицензией CI не пропустит.
- Появился Issue «Контракт изменился» → прочитай и адаптируй свой код.

## 2. Зоны владения — главное правило команды
- Свои папки — в `docs/team/ROLE_<роль>.md`, полная карта — `tools/zones.json` (`python tools/han_zones.py who <путь>`).
- Чужие папки только читай. Нужна правка у соседа → создай Issue по шаблону «Задача для другой зоны» (метка `zone-x`), пока используй заглушку.
- Общее лежит только в `contracts/` (интерфейсы между зонами, схемы данных). Менять — отдельным маленьким PR с меткой `contract`
  и описанием «зачем / кого затронет»; нужно одобрение всех (CODEOWNERS). Старая версия живёт, пока все не перешли.
- Файлы владельца (`CLAUDE.md`, `docs/design/`, `docs/team/`, `tools/`) не трогай. Видишь ошибку → напиши владельцу.
- Запрет подкреплён: `.claude/settings.local.json` (Edit-запреты), хук `.githooks/pre-push`, проверка `repo-check` в PR.
  Если проверка мешает — НЕ обходи, объясни пользователю, что именно мешает.

## 3. Git
- Один рабочий каталог — одна сессия Claude. Две сессии одновременно → два `git worktree`, каждая на своей ветке.
- Коммиты только в свою ветку, маленькие, по-русски или по-английски, с номером этапа: `G1: хит-детект по фреймам`.
- Никаких `push` в `main`, `--force`, `reset --hard origin`, переписывания чужой истории. В `main` — только через Pull Request.
- PR открывай хотя бы раз в 1–2 дня (даже маленький) по шаблону; сборка и тесты — зелёные до PR.
- Конфликт в чужом файле → не решай «своей версией»; остановись и сообщи пользователю.

## 4. Данные, тексты, ассеты (чтобы не ловить конфликты и юридические проблемы)
- Числа — только в данных (`data/**`), не в коде. Тексты — только ключи локализации; файлы по зонам: `data/loc/<язык>/<зона>.csv`
  (`engine`, `combat`, `ui`, `story`, `world`, …) — один общий csv запрещён. Папка `data/loc` — зона B; A кладёт свои строки в `contracts/loc_requests/A.csv`, B переносит.
- Новый ассет: сначала лицензия (только CC0/CC-BY/свободные), затем запись в `docs/credits/<роль>.md`
  (колонки: Ассет | Автор | Источник URL | Лицензия | Где используется | Изменён?). Без записи ассет не коммитится.
- Ассеты можно и нужно искать в интернете и переделывать под игру — **по части 76 дизайна** («Ассеты из интернета»): допустимые лицензии, источники,
  конвейер переделки (Blender-скрипты), «корёизация», чистка брендов, культурная точность. NC/ND, рипы из игр, «без лицензии» — никогда.
- Карта — это Сеул **и область вокруг** (части 72–75): посёлки, деревни, побережье, горы, храмы, общественные места, текстуры всей карты.
  В святых местах драка невозможна; действующие храмы, церкви, мечеть — с вымышленными или описательными названиями.
- Реальные бренды, имена, логотипы, марки машин, чужая музыка — запрещены. Используй пародийную вселенную (часть 13 дизайна).
- Большие исходники в Git не кладём (`assets_bin/` в .gitignore); только манифест и скрипты загрузки. Мелкие свои файлы — через Git LFS.
- Детей и подростков в игровом контенте нет (правило проекта).

## 5. Переопределения общего промта для команды (где дизайн и это расходятся — прав этот файл)
- «PROGRESS.md» → твой `docs/progress/<роль>.md`. «CREDITS.md» → `docs/credits/<роль>.md` (склеивает `tools/merge_credits.py` на E15).
- «ARCHITECTURE.md» → `docs/arch/<роль>.md` (индекс ведёт A). «docs/scripting.md» ведёт B.
- Модули ragdoll и ткань (XPBD) вынесены из `han/physics/` в `han/ragdoll/` и `han/cloth/` (зона B): у каждой папки один хозяин. Остальная структура модулей — как в части «Движок».
- Раздел «Первое задание» из дизайна заменён на `docs/team/FIRST_TASKS.md`. Дизайн уже разложен по частям — повторять не нужно.
- Корневые `CMakeLists.txt`, `CMakePresets.json`, `vcpkg.json` ведёт только A: он сразу объявляет ВСЕ библиотеки из части «Движок»
  и автоматически подхватывает модули (`han/*/CMakeLists.txt`, `game/*/CMakeLists.txt`, `tests/*/CMakeLists.txt`).
  Остальным в корне править ничего не нужно; нужна библиотека → Issue для A.

## 6. Качество и конец сессии
- Перед PR: сборка, тесты, замер производительности своего модуля (бюджеты — части «Производительность» и «Память»).
- Definition of Done — в конце `docs/design/64_tehnicheskie_prilozheniya.md`. Этап закрывается, только когда выполнены ВСЕ пункты.
- В конце сессии обнови `docs/progress/<роль>.md`: что сделано, что дальше, что нужно от других (с номерами Issues), блокеры.
- Не придумывай факты о проекте: нет ответа в дизайне → спроси пользователя (не больше 3 вопросов за раз).
- Не делай мультиплеер, универсальный редактор уровня и не пиши свои физику/звук/UI-движок поверх готовых библиотек.
